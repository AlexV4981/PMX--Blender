# Stage 03 Qwen3.5-0.8B weight trial: three failed inventory responses

The installed Qwen3.5-0.8B model and two small, separate weight edits failed a single read-only Blender geometry-inventory task for Lynae. None produced a usable inventory, and none was executed in Blender. The edited checkpoints are rejected for this task; this experiment does not qualify or disqualify the model on broader Blender work.

## What was compared

The source was `Qwen/Qwen3.5-0.8B` at Hugging Face revision `2fc06364715b967f1860aea9cf38778875588b17`. Its one safetensors shard has SHA-256 `04b1c301231dd422b8860db31311ab2721511346a32cb1e079c4c4e5f1fe4696`; the source hash remained unchanged. This was a Hugging Face BF16 comparison, not a comparison against the separate Ollama GGUF install. The two patched checkpoints were cloned independently from that source.

All three runs used the same stage03 prompt and runner hash, CPU BF16, eager attention, eight threads, greedy decoding, thinking disabled, seed 0, and a 1,536-new-token cap. The prompt asked for a **read-only, JSON-serializable inventory** of the open disposable scene: mesh and shape-key counts, zero-area faces, loose vertices, nonmanifold edges, duplicate polygon topology, material slots, and modifier order. Lynae was evaluation-only; no user asset or OpenAI-authored output was used as a training label. The exact raw responses and patch verification records remain local in the lab's ignored `data/` directory rather than this public report.

The v1 edit targeted `q_norm` in the six full-attention layers 3, 7, 11, 15, 19 and 23. The v2 edit targeted both `q_norm` and `k_norm` in those layers, giving an approximate 3.02% query–key dot-product scale increase before BF16 rounding. BF16 rounding meant fewer scalars actually changed than requested: 1,517 for v1 and 3,037 for v2, out of 873,438,784 source parameters. The maximum observed per-region relative L2 changes were 0.03113 and 0.04664, respectively, below the lab's 0.05 cap; both global edited fractions were below 0.0002. No other tensors were changed in the recorded patch verification. Neither edit used training, gradients, a loss function, or a demonstrated causal link between these tensors and Blender API knowledge. Codex chose coarse attention-scale probes to test response sensitivity, not to repair an identified weight defect.

The intact response used invalid Blender properties and collections such as `Object.vertices`, `Object.faces`, `Object.material`, and global `bpy.data.polygons`. Its nonmanifold logic was inverted, and its duplicate-topology test compared a value with itself. V1 retained invalid API access and added an unobserved zero-count inventory for a purported Lynae mesh. V2 still used invalid Object/global mesh properties, shape-key geometry fields and an unsupported edge property, and repeated the tautological duplicate check. The scripts parsed as JSON and Python after removing a terminal model token; no code was corrected, run, or trusted on that basis. Their explanations described checks the code could not perform.

The shorter v2 generation time is not evidence of better geometry competence: all three responses failed the same task. One case cannot establish a failure rate, general model capability, or the cause of the errors. The interventions were too coarse to teach verified Blender API usage, and the results provide no basis to promote either patch. The original Codex stage03 workflow is the fallback. Any future specialist experiment needs official API context, narrower independently verified fixtures, held-out Blender execution and reviewer evidence; training data must satisfy the lab's provenance rules. This report does not assert that a larger model is required.

## Original stage03 fallback

Codex inspected the unchanged Lynae r3 candidate in Blender 5.2.2. The character mesh had 90,865 source vertices, 125,942 source polygons and 146 shape keys with matching vertex counts. The native post-armature hair filter evaluated to 104,740 polygons while retaining the source-face correspondence attribute. The read-only inventory found zero zero-area polygons at a 1e-12 threshold, zero loose vertices, zero edges used by more than two faces, and zero repeated polygon vertex sets. The layered mesh has open boundaries, which were not treated as defects. This vertex-ID topology check does not detect coordinate-coincident faces on separate vertex IDs; the earlier hair repair was checked separately. No further geometry change was justified, so stage03 has a byte-identical no-change review candidate. Full rig/motion qualification and human stage03 acceptance are still pending.

Blender wrote the diagnostic JSON twice with identical hashes, but the background process stalled on exit with a PulseAudio wake error; those commands are not claimed as clean process passes. The HF completion hook wrote a durable process-success marker for v2. Its optional desktop notification could not connect in this environment, and a completion marker does not validate model output or approve a stage.
